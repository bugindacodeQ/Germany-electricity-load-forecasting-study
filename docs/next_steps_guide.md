# Senior data science project guide

Use this as the working sequence for the Germany hourly load-forecasting case study. Each stage should answer a decision or resolve a material uncertainty before adding more modelling complexity.

## Current project status

- Selected target: hourly German actual load (MW).
- OPSD data audited; Prophet, holiday-aware Prophet, Ridge, gradient boosting, and a small neural network have been compared.
- Gradient boosting is promising, but its apparent 2020 MAE advantage over the published forecast is small and unstable by month.
- The published forecast in OPSD has no per-row issue or revision timestamp. ENTSO-E describes publication deadlines and update rules, but this export does not preserve the forecast vintage.
- **2020 results have already been inspected. Treat 2020 as a historical reference, not as a clean untouched test for future model selection.**
- The project still lacks an operator's real decision, cost of forecast errors, archived forecast vintages, and archived weather forecasts.

## Work sequence

### 1. Lock the business question

Write down who would use the forecast, the forecast cutoff, the target geography, the 24-hour horizon, and the action it informs. Ask what underforecasting and overforecasting cost. Keep the present public-data study framed as grid-level forecast evaluation until an operator confirms a real decision and supplies relevant cost data.

**Gate:** a named user, action, cutoff, and primary metric are documented.

### 2. Establish data provenance and vintage

**Status:** Source fields, time conventions, missing intervals, and forecast-vintage limitations are documented in `docs/data_provenance.md`. The OPSD forecast vintage and operational cutoff remain unresolved; treat its comparison as historical reference.

Trace each load field to its source and definition. Confirm time zone, daylight-saving treatment, aggregation, missing intervals, revisions, and historical methodology changes. For the published forecast, obtain issue and revision timestamps if available. Separate target timestamp from the timestamp when a forecast value became available.

**Gate:** every model input has a documented source and known availability time. If forecast vintages cannot be recovered, label the published forecast comparison as an export-to-export historical reference.

### 3. Freeze a reproducible evaluation protocol

**Status:** Protocol recorded in `docs/evaluation_protocol.md`. The 2017–2019 folds and 2020 reference were already inspected, so they are development diagnostics only. A later unseen holdout is required for a final performance claim.

Keep a single timestamped dataset extract and a documented row-selection rule. Preserve the currently reported 2020 results as reference only. For further model selection, use expanding-window or rolling-origin validation folds entirely before 2020, with all preprocessing fitted separately inside each fold. Use the same forecast hours for all methods.

**Gate:** the split, cutoff, features, metrics, and selection rule are fixed before the next model comparison.

### 4. Diagnose errors and data shifts

**Status:** Historical fold diagnostics are recorded in `reports/forecast_error_diagnostics.md`, generated by `scripts/diagnose_rolling_errors.py`. Error slices cover season, local hour, weekday, holiday status, and demand decile; annual and monthly load summaries check distribution shifts. These findings are descriptive because the years have already been inspected. Formal change-point and residual-autocorrelation tests remain open.

Use validation folds to examine error by season, local hour, weekday, holidays, demand level, and abrupt changes. Compare actual load distributions and forecast bias across years. Investigate large residuals against source data before interpreting them as model failures. State hypotheses separately from demonstrated causes.

**Gate:** each proposed model change corresponds to a specific, repeatable error pattern.

### 5. Build features from information available at issue time

**Status:** Candidate feature audit is recorded in `docs/feature_availability.md` and checked by `scripts/audit_feature_availability.py`. The calendar and 48/168/336-hour load-lag timestamps pass the assumed cutoff test; source release latency and revisions remain unverified. No archived day-ahead weather forecast source is currently established.

Start with load lags, rolling summaries computed only from past data, local calendar features, German public holidays, and day-ahead weather forecasts if archived forecasts are available. Do not use realized weather, same-day actual renewable generation, or realized prices in a day-ahead model. Document each feature's availability.

**Gate:** a feature-availability table confirms no future information enters the forecast.

### 6. Compare models on validation folds

**Status:** Locked Ridge, gradient boosting, neural-network, Prophet, and naive baselines were compared on common expanding 2017–2019 folds. Outputs and paired day-bootstrap comparisons are in `reports/expanding_window_model_comparison.md`; reproducible code is `scripts/compare_models_folds.py`. Results are exploratory because the folds were previously inspected. Gradient boosting has the lowest pooled MAE, but its difference from the neural network is uncertain; the OPSD forecast is still an unverified-vintage reference.

Retain seasonal-naive and published-forecast references. Compare regularized regression and gradient boosting first; add Prophet or a neural model only when it addresses a documented pattern. Tune only within pre-2020 validation folds. Track MAE, RMSE, bias, peak-demand MAE, and uncertainty across folds and months. Prefer the simpler model when improvements are small or inconsistent.

**Gate:** improvement is repeatable across folds and operationally meaningful, not just a lower aggregate score in one period.

### 7. Translate errors into operational value

**Status:** `reports/forecast_value_assessment.md` defines a decision-level cost framework and reports directional error exposure without assigning financial value. The value gate remains open because there is no participating operator, confirmed action, incumbent forecast vintage, or cost model. Reproducible directional summaries are generated by `scripts/assess_forecast_value.py`.

For an actual firm or system operator, map forecast errors to its decisions and costs. Estimate the impact of under- and overforecast separately, compare against the current process, and state assumptions. Do not translate MW MAE directly into money without an operating cost model.

**Gate:** a stakeholder can explain what action changes and how the value would be measured.

### 8. Communicate and hand off

**Status:** Local handoff package is prepared: README/setup commands, pinned dependencies, technical/business summary, reproducible scripts, notebook, reports, and Power BI CSV export instructions. A Power BI Desktop `.pbix` file is not included. This project folder is not a Git repository and has not been published.

Use Power BI for an explorable view of actual load, forecasts, errors, periods, and demand segments. Include definitions, missing-data handling, UTC/local-time labels, model version, and caveats. Keep the notebook and scripts reproducible from a clean checkout and include one-page findings for a technical and business audience.

**Gate:** another analyst can reproduce the scores and a stakeholder can understand the decision implication without reading model code.

## Remaining gates after the eight-step portfolio work

1. Identify an actual operational user and confirm the target, delivery-time convention, forecast cutoff, and decision.
2. Obtain incumbent forecast vintages and operational data needed to replay that decision.
3. Agree on asymmetric costs, deployment costs, materiality, and risk limits before a value pilot.
4. Secure a later untouched chronological holdout; retain current periods as development/reference evidence.
5. Review the local project package before any GitHub publication. No repository initialization, commit, or publication has been performed.
